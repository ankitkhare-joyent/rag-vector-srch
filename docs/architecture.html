Runbook RAG: hybrid search over EC2 runbooks, secrets from OpenBao

26 operations documents become 118 chunks in Postgres with pgvector. Questions run through vector and full-text search, are fused and reranked, and Claude answers with native citations. No service holds a static password: OpenBao issues every database user and the Anthropic key at runtime.

question → answer corpus → index (ingest) secrets and identity (OpenBao) host ports are published on 127.0.0.1 only

Question to cited answer

  1. A client calls POST /ask on the API, or an agent calls search_runbooks on the MCP server, which forwards to /search.
  2. The API embeds the question with bge-small (query mode) and runs one SQL statement: HNSW cosine top 30 and full-text top 30, fused with reciprocal rank fusion.
  3. A cross-encoder reads the question with each candidate and reorders them; the top k survive.
  4. Pipeline mode sends those chunks to Claude as search_result blocks. Agentic mode gives Claude the search and read tools and loops up to 6 calls.
  5. Claude's answer carries search_result_location citations, returned as numbered sources.

Corpus to index

  1. The ingest job reads 26 markdown files with front matter (runbooks, policies, guides, postmortems).
  2. Unchanged files are skipped by content hash; changed ones are split by heading, keeping code blocks and tables whole, each chunk prefixed with its document and section.
  3. Chunks are embedded in batches and written in one transaction per document; the full-text column is generated by Postgres.
  4. It connects as a writer user that OpenBao created for it, valid for 15 minutes.

Secrets and identity

  1. ① The API logs in with AppRole (role_id + secret_id from its own read-only volume) and gets a 1-hour token with policy rag-api.
  2. ② With that token it reads secret/rag/anthropic and requests database/creds/rag-reader.
  3. ③ The ingest job does the same with rag-ingest and gets writer credentials, and no LLM key.
  4. ④ OpenBao connects as bao_admin to create each user, and drops it when the lease ends.
  5. ⑤ bao-bootstrap initialises and configures OpenBao on every up, idempotently, and rotates bao_admin's password so only OpenBao knows it.
  6. ⑥ It writes a fresh secret_id per service; compose mounts only that service's subfolder.

How a database credential lives and dies

Observed on this stack over four hours: the API asked for a new Postgres user once two thirds of the 1-hour lease had passed (every 40 to 60 minutes, at the next new connection), its pool recycled connections every 30 minutes, and OpenBao dropped each old user when its lease ended. At most two dynamic users overlap.
